# D-020 切檔與任務再拆提案（architect，2026-09-02）

- 狀態：**提案，待使用者/orchestrator 裁決**。本提案不改動 `design/D-020-multi-event-per-group.md`。
- 範圍：只處理「怎麼切」；**不改任何已核可的設計決定**。發現的問題一律寫在 §五。
- 註：本檔名符合 `design/D-*.md` glob，故自身受 120 行上限（已控制）。若 harness 另有「三段式結構」
  檢查，建議改置 `docs/proposals/`；請 orchestrator 確認。

## 一、裁定：任務太大（主因），文件太長只是症狀

證據（皆取自 D-020 本文，非新判斷）：

1. §0 自陳有 **3 個正交關注點**（解除限制／消歧義／open 數上限），另有第 4 個獨立守門（§3 開團查重）。
2. 一次動 **4 個 §4.5 高風險模組** + 1 個 migration + 1 張新表 + 2 個新純函式檔（`selector.ts`、
   `event-disambiguation.ts`）+ 1 個**破壞性介面變更**（`findActiveByGroup` 移除，G1）擴散到 6 個呼叫端。
3. **30 條 AC / 15 條 Guardrails**。以 R1 上限 120 行反推，6 倍超標 ≈ 6 份文件的體量。
4. 單一 PR 無法滿足 CLAUDE.md §3.4「小步提交」，也無法獨立回滾：migration 與 handler 改寫綁在一起。

規則七「超出預算多半代表任務該再拆一層」在此**字面成立**。純切檔（選項 b）只是把同一份閱讀成本
換個路徑，T-033 仍是一次性大 PR；若把附屬文件刻意放在 check glob 之外（如 `design/annex/`），
等同規避 120 行上限。**故採 (a) 拆任務為主、(b) 的切檔機制為輔**（D-020 降級為 umbrella 索引）。

## 二、建議切法：5 個可獨立上線的任務 / 8 份子文件 + 1 份 umbrella

文件粒度由「閱讀成本」決定、任務粒度由「可獨立驗收上線」決定，兩者**不必 1:1**（故有任務帶 2 份文件）。

| 任務 | 子文件 | 風險 | 單獨上線後系統是否自洽（關鍵） |
|---|---|---|---|
| T-033a 解鎖 schema + 讀取路徑 + 消歧義核心 | D-021, D-023 | R2 | **是**。0006 雖已 DROP `ux_events_active_group`，但 §3 尚未落地→`開團` 入口仍保留「已有 active 就拒絕」，使用者**無法**建立第二場。唯一可能產生多場的路徑是「兩人自 0 場同時 `確認`」的極窄 race；若真發生：無資料損壞（鎖粒度本就是單一 event 列、不影響超賣防護），讀取指令回既有 `ambiguous` 提示（D-023 同任務落地），等其中一場過期或關閉即恢復。**可上 PROD。** |
| T-033b `名單` 0-候選回退修正 | D-022 | R1 | **是**。候選 ≤1 時行為與現況逐字相同（純判斷順序修正）；bug 只在多場並存時才顯形。 |
| T-033c 機制 B `@selector` | D-024 | R1 | **是**。純函式 + formatter；候選 ≤1 時 `resolveTargetEvent` 回 `single`、完全略過 selector（AC-6），使用者無感。 |
| T-033d 機制 A quote + dispatch/批次/grouping | D-025, D-026 | R2 | **是**。`message_event_map` 開始累積映射（上線後即有資料，等 T-033e 開燈時 quote 立即可用）；候選 ≤1 時仍回 `single`，無感。含 B1/G14 跨群校驗。 |
| T-033e 開團查重 + 同群 open 上限 3 場 | D-027, D-028 | R2 | **是，且這是 feature 開燈**：移除 `already_active` 入口拒絕，多場並行**此時才對使用者開放**；同一次同時裝上兩道新守門（查重、上限），不存在「無守門」的空窗。 |

**排序關鍵決定（新增，需複審）**：`DROP ux_events_active_group` 放在 **T-033a（早）** 而非 T-033e（晚）。
理由：(i) 晚 DROP 會讓 T-033a~d 的多場並存 AC（AC-2/18/23…）在測試 DB 上**無法構造真實狀態**，只能靠
fixture 手動砍索引（schema 與 PROD 分歧，品質風險更大）；(ii) 早 DROP 的殘餘風險已如上表論證為有界。
**連帶**：`confirm()` 的窄捕捉必須在 T-033a 就改比對新索引名（否則舊名已不存在，同場地+時間 race 會噴
未捕捉 23505）→ 故 **G8 與 AC-5 隨 T-033a 走**，不留在 T-033e。

## 五、風險與「零改動」的機械保證

- **R-1（最大風險）：拆任務必然新增內容，這部分不是搬移。** 新增的僅限「相位順序 + 中間狀態不變式」
  （§二表格右欄與排序關鍵決定）。其中「DB 已不硬擋、應用層仍擋」這段期間**從未經 R2 審過**，
  必須由 architect-reviewer + design-reviewer 重審該節。我已把它集中寫在一處，方便單點審查。
- **R-2：逐字保真的驗證方式（建議列為切檔任務的 AC）**：(a) §三 分配表 union 檢核＝15 G／30 AC 各恰一次；
  (b) 腳本比對：串接 8 份子文件的「設計內容／Guardrails／AC」段落，正規化空白與標題階層後，與
  `git show <base>:design/D-020-multi-event-per-group.md` 的 §一~§三 做 diff，**差異須僅為**標題階層、
  4 行 header、`來源：D-020 §x` 註腳；(c) reviewer 只審該 diff 的「新增行」清單，不重讀全文。
- **R-3：規則衝突（請 orchestrator 裁決，我不自行認定）**——`harness/TOKEN-BUDGET.md` 規則四寫
  「R2：完整 D-xxx，**不設上限**」，但 `check_doc_budget.py` 對所有 `design/D-*.md` 一律 120 行。
  兩者矛盾。本提案**不依賴**此裁決（即使裁定 R2 豁免，任務仍該拆），但規則本身應修正其一。
- **R-4：CLAUDE.md §5「R2 的 Guardrails 至少 3 條」**在機械分配後，D-025（2）／D-027（1）／D-028（1）
  不滿足。**不得為湊數新增 Guardrail**（那等於新增設計決定）。建議裁決「以 `沿用 D-020 Gx` 引用方式
  繼承共用 Guardrail 並計入條數」，或將這幾份子文件的風險等級依其實際觸及模組單獨評定。
- **R-5：設計本身未發現需修正之處。**唯一觀察（不構成 blocker、不改設計）：§3.5 的 race window 論述與
  §1 的「不設 DB 約束」互相自洽，拆檔後兩者分屬 D-028／D-021，需在 D-028 內以一行交叉引用保留脈絡。
