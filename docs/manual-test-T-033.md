# 真機測試腳本 — T-033a / T-033b / T-033c（多場並行）

> **這份腳本是 T-033c 的 DONE 條件之一**（使用者裁決 2026-09-02，非選項）。
> 使用者裁決同時要求：**真機驗證延後到 T-033c 上線後一次做完**，不再分三批測。
>
> **成本上限（使用者裁決 2026-09-06）**：**只用 2 個 LINE 帳號、2 個群組**。
> 本腳本已依此重新設計——見 §0.5「兩帳號怎麼把授權測完」。
>
> **怎麼用**：從 §0 開始，由上而下**照著打**。每一步都寫出「要打的字」（可直接複製）與
> 「預期回覆」（逐字，含標點）。**不需要回頭讀任何設計文件。**
> 每一步都標了對應的 AC 編號，失敗時直接拿編號對回 `design/D-0xx`。
>
> **⚠️ 先讀 §0.4「本腳本刻意不逐字斷言的三種地方」**——那三種地方逐字對不上是正常的，
> 不要當成 bug；反過來說，**其餘每一個字都應該一模一樣**，對不上就是 bug。

## 0. 前置設定

### 0.1 需要的 LINE 帳號（**只要 2 個**）

| 代號 | 角色 | **硬性條件** |
|---|---|---|
| **甲** | 一般帳號 | 其 LINE userId **絕對不可以**出現在 `ADMIN_USER_IDS` |
| **乙** | **super-admin** | 其 LINE userId **必須**在 `ADMIN_USER_IDS` 內 |

> **這兩個條件缺一不可，否則 §3 會測出假結果**：
> §3 D1 要驗「非主辦**且非管理員**會被拒」——甲若剛好是 admin，那步會變成通過而測不出漏洞；
> §3 D2 要驗「super-admin 可跨主辦操作」——乙若不是 admin，那步會被拒而誤判為 bug。
>
> **開始測試前先確認**：兩個帳號各打一次 `我的ID`，把回覆的 userId 拿去對 `ADMIN_USER_IDS`。

### 0.2 需要的 LINE 群組（**只要 2 個**，bot 都要加進去）

| 代號 | 用途 | 起始狀態 |
|---|---|---|
| **G1** | 單場零回歸 → 多場並行 → 授權 → 上限 | **必須沒有任何進行中的活動** |
| **G2** | 開團查重 →（清空後）過期相位 | **必須沒有任何進行中的活動** |

> **「沒有任何進行中的活動」怎麼確認**：在該群打 `名單`，回覆必須是
> `目前沒有開放報名的活動。`
> 若不是，請先由該場的建立者打 `取消活動` 清乾淨，**再開始測試**。
> 兩個群不可共用：G1 全程會累積到 3 場活動（上限測試需要），
> 而 G2 的過期測試**必須在 0 場進行中的狀態下開始**（見 §6 G0）。

### 0.3 日期代號（**開始前先填好，後面全部照填**）

| 代號 | 定義 | 斜線式（**打字用**） | 橫線式（**回覆裡會出現**） |
|---|---|---|---|
| **D1** | 測試當天 **+7 天** | `________`（如 `2026/09/13`） | `________`（如 `2026-09-13`） |
| **D2** | 測試當天 **+8 天** | `________` | `________` |
| **D0** | 測試當天 **前一天**（昨天） | `________` | `________` |

> **為什麼 D1 特地取「+7 天」**：系統在提示訊息裡帶出的範例日期就是「今天 +7」，
> 取同一天可讓 §5／§6 的開團提示也能逐字核對。

**顯示名**：預期回覆裡的 `甲`／`乙` 一律代表**該帳號在該群的 LINE 顯示名**，請自行代換。
同一人的第 2、3、4… 個名額顯示為 `名字(2)`／`名字(3)`／`名字(4)`。

### 0.4 本腳本刻意不逐字斷言的三種地方（對不上是正常的）

1. **`分組` 的組員名字與順序**——`partitionBalanced` 內部用 `shuffle` 隨機排列，
   **不可能**逐字預期。只驗**組數**、**每組人數**、以及固定句（如「（人數 5，暫不拆組）」）。
2. **`@` mention 的實際標註效果**——是否真的變成藍字可點屬 LINE 客戶端呈現，腳本只驗文字內容。
3. **顯示名本身**——見 §0.3 最後一段。

除這三項外，**每一個字（含標點、全形括號、驚嘆號）都應該一模一樣**。

### 0.5 兩帳號怎麼把授權測完（設計說明，不用照做）

原始設計要 4 個帳號（主辦 A／主辦 B／一般成員／super-admin）。壓到 2 個的作法是
**讓同一個帳號在不同活動上扮演不同角色**：

| 測項 | 需要的身分關係 | 本腳本怎麼滿足 |
|---|---|---|
| §3 D1 非主辦被拒 | 執行者**非該場主辦、非 admin** | 大屯是**乙**開的，由**甲**（非 admin）去操作 |
| §3 D2 super-admin 跨主辦 | 執行者**是 admin、非該場主辦** | 東方 14:00 是**甲**開的，由**乙**（admin）去操作 |
| §1 一般報名 | 非主辦者報名 | 東方 08:00 是**甲**開的，由**乙**報名 |

> 代價：少了「兩個不同的一般成員」這種組合（例如兩人同時報名的名額競爭）。
> 那類情境不屬 T-033a~c 的變更範圍，且由 549 條自動化測試覆蓋。

### 0.6 相位對照（哪一項在哪個版本才可測）

| 相位 | 版本 | 章節 |
|---|---|---|
| A | T-033a 後即可測 | §1 全部 |
| B | T-033b 後才可測 | §2 的 C2（引言） |
| C | **T-033c 後才可測**（多場並行對使用者開燈） | §2 除 C2 外全部、§3、§4、§5、§6 |

> **T-033c 未上線前，§2～§6 全部不可測**——開團入口會擋掉第二場，多場並行根本開不出來。

## 3. 授權的「作用對象」必須是被選中的那一場（G1）〔D-020 AC-23〕

> **這是多場並行最容易出安全漏洞的地方**：授權要對「selector 選中的那一場」判斷，
> 而不是對「群組裡隨便一場」判斷。

### D1. 非該場主辦、又非 admin → 拒絕

**甲**（東方兩場的主辦，但**不是**大屯那場的主辦，且**不在** `ADMIN_USER_IDS`）打：

```
@大屯 取消活動
```

**預期回覆（逐字）**：

```
只有開團的人（或系統管理員）可以關閉報名／取消活動。
```
